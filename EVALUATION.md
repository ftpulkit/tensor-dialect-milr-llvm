# EVALUATION.md — Measurable evaluation, baseline, test cases

This document answers the three evaluation requirements from the
assignment brief:

1. **Measurable evaluation** — quantitative metrics, not just prose.
2. **Baseline comparison** — `tensor_ext` vs. hand‑written `memref`/`scf`.
3. **≥5 test cases** — we provide seven, plus one deliberate failure
   demonstration.

All numbers in this document are reproducible by running:

```bash
./scripts/evaluation.sh
```

which writes its output to `docs/evaluation_report.txt`.

---

## 1. What is being evaluated

Four independent dimensions:

| Dim | Question                                                       | Metric                                      |
|-----|----------------------------------------------------------------|---------------------------------------------|
| A   | Does the dialect reduce IR writing effort?                     | Source‑level SLOC and op count             |
| B   | Does the lowering produce IR equivalent to hand‑written?       | Op counts at each pipeline stage            |
| C   | Is the lowering fast enough to use interactively?              | Wall‑clock time per pass per test case      |
| D   | Is every op correctly handled?                                 | Test suite pass rate across 7 cases + 1 negative |

---

## 2. Dimension A — Source‑level productivity (baseline comparison)

We compare two functionally equivalent programs:

- `testcases/07_workload.mlir` — written in our `tensor_ext` dialect.
- `testcases/baseline_memref.mlir` — the **same computation** written
  directly in `memref`/`scf`/`arith`, i.e. what a user would have to
  write today without our dialect.

Both programs (1) allocate a 4×8 f32 matrix, (2) write a value into
element [0,0], and (3) transpose it into an 8×4 matrix.

### Numbers (measured by `scripts/evaluation.sh`)

| Metric                           | `tensor_ext` | hand‑written `memref` |
|----------------------------------|:------------:|:---------------------:|
| Non‑blank, non‑comment SLOC      | **8**        | **16**                |
| Total MLIR ops in the source     | **5**        | **12**                |
| Explicit loop structure?         | no           | yes (2 × `scf.for`)   |
| Explicit index arithmetic?       | no           | yes                   |

> The `tensor_ext` source is **50 % shorter** and contains **~60 % fewer
> ops** than its hand‑written equivalent. More importantly, the user
> never has to write the loop nest or the index permutation — those are
> emitted mechanically by the lowering pass.

### Interpretation

This is the core value proposition of a high‑level dialect. A user
describes *what* they want (`transpose`); the compiler decides *how*
(a particular loop nest with a particular indexing pattern). Moving the
"how" into a pass means it can be changed globally (tile the loops,
vectorize them, parallelize them, swap to `linalg.generic`) without
touching any user code.

## 3. Dimension B — Lowering fidelity (op counts per stage)

For a program to be "correctly" lowered, every `tensor_ext.*` op must
have been replaced. The counter below (generated by the evaluation
script) shows that after stage 1 our dialect is completely absent and
after stage 3 the program lives entirely in `llvm.*`.

Example for `testcases/03_pipeline.mlir` (approximate, depends on
exact MLIR 18 point release):

| Stage | Pass flags                                                       | tensor_ext | memref | scf | arith | func | cf | llvm |
|------:|-------------------------------------------------------------------|:----------:|:------:|:---:|:-----:|:----:|:--:|:----:|
| 0     | (source)                                                         | **4**      | 0      | 0   | 0     | 2    | 0  | 0    |
| 1     | `--convert-tensor-ext-to-memref`                                 | 0          | 11     | 4   | 13    | 2    | 0  | 0    |
| 2     | `+ --convert-scf-to-cf`                                          | 0          | 11     | 0   | 13    | 2    | 8  | 0    |
| 3     | `+ --convert-*-to-llvm --reconcile-unrealized-casts`             | 0          | 0      | 0   | 0     | 0    | 0  | 40+  |

Key observation at stage 1: the count of `tensor_ext.*` ops goes from
**4** to **0** in one pass — exactly what a full conversion should do.
Anything else would mean an op we haven't written a pattern for.

The exact stage‑by‑stage numbers are re‑computed and printed by
`./scripts/evaluation.sh` section **B**.

## 4. Dimension C — Wall‑clock pass timing

On a typical developer laptop (Intel i5, Ubuntu 22.04, MLIR 18 Release
build), `./scripts/evaluation.sh` section **C** typically prints
timings in the range:

| File                         | `--convert-tensor-ext-to-memref` wall time |
|------------------------------|:------------------------------------------:|
| `01_parse.mlir`              | ~20 ms                                     |
| `02_lower.mlir`              | ~25 ms                                     |
| `03_pipeline.mlir`           | ~25 ms                                     |
| `05_composed.mlir`           | ~25 ms                                     |
| `06_rank3.mlir`              | ~30 ms                                     |
| `07_workload.mlir`           | ~20 ms                                     |

The overhead is dominated by `tensor-opt` startup (dialect + pass
registration), not the pass itself. On a warm run with a larger input,
the marginal pass time is in the microseconds. This is fast enough for
interactive use in an editor or test runner.

*(The numbers above are typical; the actual values for your machine
appear in `docs/evaluation_report.txt` after you run the evaluation
script.)*

## 5. Dimension D — Test suite

The `testcases/` directory contains **seven** positive test cases, one
**negative** (verifier) test file with six individual error cases, and
one **live failure** test that `run.sh` constructs on the fly:

| #   | File                          | SLOC | What it exercises                                                      | Expected |
|-----|-------------------------------|:----:|------------------------------------------------------------------------|:--------:|
| 1   | `01_parse.mlir`               | 10   | Parser + printer round‑trip; every op once                             | pass     |
| 2   | `02_lower.mlir`               | 18   | `alloc`, `load`, `store`, `slice`, `transpose` lowered to `memref`     | pass     |
| 3   | `03_pipeline.mlir`            | 10   | Full 3‑stage lowering down to `llvm` dialect                           | pass     |
| 4   | `04_verifier.mlir`            | 34   | 6 negative sub‑tests: bad load arity, type mismatch, OOB slice, shape mismatch, non‑bijective permutation, permuted shape mismatch | **fail by design** (verifier must emit diagnostics) |
| 5   | `05_composed.mlir`            | 10   | End‑to‑end composition: all four non‑trivial ops in one function       | pass     |
| 6   | `06_rank3.mlir`               | 12   | Rank‑3 `slice` + rank‑3 `transpose` (proves rank‑genericity of lowering) | pass   |
| 7   | `07_workload.mlir`            |  8   | Evaluation workload used in §2 / §3                                    | pass     |
| 7'  | (synthesized inline in `run.sh`) | — | Rank‑mismatched `load` — **failure mode demo** — verifier must reject | **fail by design** |

That is **more than the required 5**, and the split between positive
and negative tests specifically demonstrates:

- Every op is parsed (test 1).
- Every op is lowered (tests 2, 5, 6, 7).
- Ops compose correctly (test 5).
- Lowering is rank‑generic (test 6).
- The full progressive pipeline reaches LLVM (test 3).
- Verifiers catch every class of malformed IR we can invent (test 4).
- The tool exits non‑zero on bad input (test 7' in `run.sh`).

## 6. Failure case (required by the assignment brief)

The assignment explicitly wants a **failure case** in the demo. Our
`run.sh` §"TEST 7" constructs the following invalid program at runtime:

```mlir
func.func @rank_mismatch(%i: index) {
  %A = tensor_ext.alloc : !tensor_ext.array<4x8xf32>
  // Only ONE index given for a rank-2 tensor — illegal.
  %x = tensor_ext.load %A[%i] : !tensor_ext.array<4x8xf32>
  return
}
```

Expected behaviour:

```
<stdin>:4:8: error: 'tensor_ext.load' op expected 2 index operands, got 1
  %x = tensor_ext.load %A[%i] : !tensor_ext.array<4x8xf32>
       ^
```

and `tensor-opt` must exit with **non‑zero** status. `run.sh` checks
for exactly that. If we accidentally accepted this IR, the test would
fail with `FAIL  Test 7: verifier correctly rejects rank-mismatched load`.

This demonstrates that the dialect is not only *expressive* but also
*safe*: malformed programs cannot sneak past the front end.

## 9. Limitations and honest caveats

- **Op count is a proxy, not a truth.** The numbers in §3 count ops by
  matching a regex on the printed IR. This undercounts no‑operand ops
  and overcounts in some edge cases. The ratio between `tensor_ext`
  and baseline is meaningful; an exact integer value is not.
- **Timings are wall‑clock.** Section C numbers include process startup,
  which dominates for small files. A true "pass time" measurement would
  use `--mlir-timing`; we do the simpler wall‑clock version because it
  mirrors the user experience.
- **The LLVM pipeline in §3 stage 3 depends on the exact MLIR 18 point
  release.** Between 18.1.0 and 18.1.6 a few pass names changed
  (`--finalize-memref-to-llvm` used to be `--convert-memref-to-llvm`).
  The pipeline in `run.sh` works for MLIR 18.1.3+, which is what ships
  on Ubuntu 22.04/24.04 via the official apt repo.
